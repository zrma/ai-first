# Work lifecycle

## Todo spec의 역할

todo spec은 milestone 또는 bounded specification의 목적, 범위, 조건과 관계를
명시해 논리적 누락·모순·미결정을 해소하는 임시 설계 계약이다. 작성 과정은 설계
검토이며, 정립된 spec은 구현과 완료 판정의 기준이다.

이 저장소의 active 작업은 `docs/todo-*/spec.md`와 `open-questions.md`에 둔다.
목적, 범위와 non-goal, 조건·의존 관계, acceptance와 검증, 중요한 결정 경계를
명시한다. 결과를 바꾸는 질문은 의존 구현 전에 해소한다. 질문 파일은 미결정과
해결 근거를 작업 중 관리하고, 구현에서 발견한 사실은 spec과 함께 갱신한다.
완료 기준의 변경은 이유와 영향을 드러내며 미충족 결과를 숨기는 수단으로 쓰지 않는다.

## 의도와 변경 전 기준

의도는 기존 spec 안에 둔다. 다음 정보가 구별되어야 하지만 고정된 제목이나 별도
`intent.md`를 요구하지 않는다. 이미 적절한 항목이 있으면 그 위치를 사용한다.

| 정보 | 답해야 할 질문 |
| --- | --- |
| 문제 | 현재 누가 어떤 문제를 겪으며 무엇이 근거인가? |
| 원하는 결과 | 변경 후 사용자가 관측할 수 있는 개선은 무엇인가? |
| 영향 | 영향을 받는 사용자·시스템·외부 계약은 무엇인가? 편집 파일 목록과 구별한다. |
| 제약 | 유지해야 할 동작과 넘지 말아야 할 경계는 무엇인가? |
| Non-goal | 이번 변경이 해결하려고 하지 않는 문제는 무엇인가? |

scope는 이번에 바꿀 영역, 영향은 그 변경이 미치는 영역, 제약은 변경 중에도 지킬
조건이다. non-goal을 새 목표로 편입하려면 범위 변경 이유와 영향을 드러낸다.
관련 제약이 없으면 검토 결과 없음을 명시할 수 있지만, 미확인 상태를 없음으로 쓰지 않는다.
acceptance에는 원하는 결과와 필요한 제약을 확인할 방법을 연결한다.

구현 중 spec을 갱신할 때 원래 기준을 VCS revision 또는 기존 versioned 기록으로
추적하고 무엇이 왜 바뀌었는지와 영향을 남긴다. spec 자체의 diff도 리뷰 대상이다.
정당한 발견으로 계획을 바꿀 수 있지만 제품 방향·제약·위험의 실질적 변경은 기존
권한 경계를 따른다. session의 승인 원문을 tracked 문서에 복사하지 않는다.

## 규모와 native lifecycle

문서량과 리뷰 깊이는 변경 위험·복잡성에 비례한다. native 규칙이 허용하는 단순
수정은 기존 issue 또는 local change 설명의 문제·결과·검증으로 충분하며 새 packet,
계획 파일 또는 PR을 강제하지 않는다. 줄 수만으로 위험을 판정하지 않는다.
API·인증·데이터 변경처럼 관계나 실패 영향이 큰 작업은 제약, 의존성, acceptance와
관련 복구·전문 검토를 충분히 기술한다. 별도의 고정 Level 체계는 요구하지 않는다.

framework는 공통 정보와 검토 기준을 제공하고 소비 저장소는 기존 work-start,
template와 readiness gate의 형식을 소유한다. 이 문서의 예시는 새 parser schema가
아니다. framework update가 기존 packet에 새 필드를 일괄 강제하지 않으며, native
검사를 강화하는 작업은 해당 저장소의 요구·호환성을 확인해 수행한다.

## 변경 리뷰와 기록

PR 유무와 관계없이 변경 전 의도·제약·acceptance, 이후 spec 변경 이유, 대상 diff와
관련 테스트·runtime evidence를 대조한다. 현재 spec이 실제 목표의 정당한 변경을
반영하는지도 검토한다. 기준이 없거나 읽을 수 없으면 누락을 표시하고, diff에서
추측한 의도를 원래 요구사항으로 확정하지 않는다.

1. 원래 문제와 원하는 결과가 실제로 해결됐는가?
2. 유지해야 할 동작·제약을 지켰는가?
3. 예상 밖 사용자·시스템 영향이나 범위 확장, non-goal 편입이 있는가?
4. spec·계획·acceptance 변경에 타당한 이유가 있으며 기존 권한 경계를 지켰는가?
5. 회귀 위험에 맞는 검증이 있는가? 미충족과 미검증은 각각 무엇인가?

PR body의 체크 표시나 구현자의 자기평가는 증거를 대신하지 않는다. findings에는
관련 기준, 실제 변경과 실패 조건을 연결하고 수행한 검증의 범위와 한계를 적는다.
추가 전문 리뷰와 다중 agent는 확인된 필요와 허용 범위에서 선택한다. 리뷰 통과는
merge·publication 권한이나 인간의 제품·위험 판단을 대신하지 않는다.

PR을 사용하는 저장소는 기존 본문에 의도, 중요한 제약·acceptance의 판정, 결정 변경,
검증 한계와 소유 artifact를 간결하게 요약한다. PR이 없으면 local change 설명과
기존 완료 요약에 같은 정보를 둔다. 요약은 원본 spec의 관리 위치를 대체하지 않는다.
새 코드가 추가되거나 기준이 바뀌면 관련 리뷰·검증과 요약을 갱신한다.

완료 후에도 당시 spec이 필요한 리뷰 기록에는 실제 존재하는 immutable commit과
경로를 사용한다. 이동하는 branch나 jj change ID만으로 당시 내용을 고정했다고
주장하지 않는다. local 기록은 commit과 repo-relative path, 공개 PR은 공개된
commit permalink를 사용할 수 있다. 공개되지 않은 revision은 외부에서 열리는
링크로 제시하지 않는다. 최종 계약은 이관된 artifact가 소유한다.

## 적용 예시와 리뷰 시나리오

아래는 retry 동작을 바꾸는 가상의 spec 예시이며 기존 native 형식에 맞춰 합칠 수 있다.

```markdown
# 재접속 부하 분산

## 의도
- 문제: 장애 복구 직후 client들이 동시에 재접속해 부하가 집중된다.
- 원하는 결과: 재시도를 시간상 분산하면서 기존 재시도 성공·실패 동작을 유지한다.
- 영향: reconnect client, 연결 복구를 기다리는 호출자, retry 테스트.
- 제약: 최대 시도 횟수, public 설정, 최초 접속 동작을 유지한다.
- Non-goal: connection pool과 failover 구조 재설계.

## 설계와 검증
- 범위: reconnect 지연 계산과 관련 회귀 테스트.
- 의존성: 테스트에서 제어 가능한 clock과 난수 입력.
- Acceptance: 지연의 허용 범위와 분산을 확인하고 최대 시도 횟수·최초 접속을 검증한다.
- 미결정: 허용 지연 범위는 구현 전에 결정하고 open-questions에 근거를 남긴다.
```

이 예시는 지연 범위가 미결정이므로 의존 구현을 시작할 수 있는 완성 spec은 아니다.
반면 문서의 오탈자 수정은 native 규칙이 허용하면 change 설명에 문제와 확인 범위를
남기면 된다. 같은 형식의 packet을 만들 필요는 없다.

| 시나리오 | 리뷰 판정 |
| --- | --- |
| 지연 테스트는 통과했으나 최대 시도 횟수도 바뀜 | 제약 위반으로 미충족. 테스트 통과만으로 완료할 수 없다. |
| 구현과 함께 최대 시도 횟수 유지 제약을 spec에서 삭제함 | 원래 기준과 spec diff를 검토한다. 이유와 필요한 인간 판단이 없으면 해결된 것으로 취급하지 않는다. |
| 부하 집중 경로에 대한 관측 없이 단위 테스트만 통과함 | 테스트로 확인한 범위와 실제 부하 개선의 미검증을 구별한다. |
| 완료 후 spec을 제거했으나 리뷰가 당시 기준을 요구함 | 실제 commit에서 spec을 읽고 최종 소유 문서와 연결한다. 삭제된 최신 경로만 남기거나 packet을 영구 보존할 필요는 없다. |

PR/local 리뷰 요약은 예를 들어 “재접속 부하 분산; 최대 시도 횟수와 최초 접속은
회귀 검증 통과; 실제 부하 개선은 미검증”처럼 증거에 맞춰 쓴다. 이는 가상 판정
예시이며 실제 테스트 성공 기록이 아니다. 당시 spec 참조와 최종 API/운영 문서는
해당 변경의 실제 경로로 연결한다.

## Artifact 전환

완료 시 spec의 acceptance와 실제 결과·검증을 대조하고 앞으로 유지할 지식을
그 지식의 소유 문서나 코드에 반영한다.

| 유지할 내용 | 적절한 위치 |
| --- | --- |
| 동작과 회귀 방지 | 구현과 의미 있는 테스트 |
| 사용법과 외부 계약 | README, 사용자/API 문서 |
| 구조, 제약, 결정 이유와 포기한 대안 | architecture 또는 필요한 decision record |
| 운영 조건, 복구 방법과 알려진 한계 | 운영 문서와 runbook |
| 완료 결과와 검증 범위 | 기존 완료 요약이나 변경 이력, 필요한 검증 artifact |
| 미완료 작업과 이후 시작 조건 | 현재 active spec 또는 handoff/status/roadmap |

artifact의 목적은 다음 참여자가 결과를 이해하고 사용하고 변경하는 데 필요한
지식을 보존하는 것이다. 별도 milestone 문서나 완료 보고서를 매번 만들지 않는다.
검증 명령만으로 과거 성공을 주장하지 않으며 수행한 범위·판정·한계를 함께 남긴다.
raw output, transcript와 machine-private evidence는 공개 tracked artifact에 넣지 않는다.

필요한 리뷰 기준의 immutable 참조, 이관과 참조 정합성을 확인한 뒤 역할이 끝난
todo spec과 질문 파일을 제거하고
현재 상태 포인터를 갱신한다. 원래 설계와 작업 과정은 VCS 이력에서 추적할 수 있다.
단순히 completed 폴더로 이동하는 것은 artifact 전환을 대신하지 않는다.
원본 보존은 감사·운영 등 명시적인 필요가 있을 때만 선택하며 보존 이유와 역사적
상태를 표시한다. 원본을 보존해도 현재 계약 문서로의 지식 이관은 수행한다.

## 검증 경계

`scripts/check.sh`는 generated drift, standalone lifecycle, 문서 참조와 harness
interface를 검사한다. standalone checker는 terminal `docs/todo-*/spec.md`를
거부한다. 파일 존재 검사로 지식 이관의 의미적 충분성을 증명할 수는 없으므로,
spec과 결과를 대조하는 완료 검토가 필요하다.
의도 항목이 있다는 사실만으로 요구사항의 타당성이나 문제 해결을 증명할 수 없다.
문서 합성·standalone 검증과 위 시나리오의 계약 검토는 실제 agent의 발견률·오탐률을
측정하는 행동 eval과 구별한다.

framework는 소비 저장소의 native work-start/finalize 명령과 domain artifact를
보존한다. 기존 completed 기록은 원본 보존 필요와 내용의 소유 위치를 검토한 범위에서
정리하며, 버전 업데이트를 이유로 소비 저장소의 과거 기록을 일괄 삭제하지 않는다.
